# TDX ticks 落库方案 v2

> 决策日期:2026-09-18(北京时间,经评审确认)
> 状态:**已批准,待落地**

---

## 1. 背景与问题

### 1.1 现有 `tbl_tick` schema(`offlineDataManager/data/policy_ticks.db`)

```sql
CREATE TABLE tbl_tick (
    ts_code TEXT NOT NULL,
    trade_date TEXT NOT NULL,
    datetime TEXT NOT NULL,
    time TEXT NOT NULL,
    seqId INTEGER,
    price REAL,
    vol INTEGER,
    buyorsell INTEGER,
    created_at TEXT NOT NULL,
    PRIMARY KEY (ts_code, trade_date, seqId)
);
```

### 1.2 三个真实问题

#### 问题 A:`seen` 去重 key 缺失 buyorsell

`tdx_client.py:446-450` 用 `(time, price, vol)` 三元组做 `seen` 去重。TDX 协议下,
**同一分钟、同价、同量完全可能有多笔真实成交**(多买方竞争同一价位)。
当前 key 缺 `buyorsell`,导致:

- 同 `(time, price, vol)` 不同 `buyorsell` 的真实成交被吞掉
- 24-cell 矩阵实测:**A 组丢 195 条/股/日,B 组丢 137 条/股/日**(B 组原始数据少所以少丢)

> GPT 在吴老师机器对账确认:`60.12.136.250` 实测 raw=4614,returned=4419,删 195 条,
> 其中 13 组是同 `(time,price,vol)` 不同 `buyorsell`。

#### 问题 B:单页失败/截断时静默返回部分数据

`tdx_client.py:432-433` 单页失败时 `return _enrich_ticks(...)` 返回已拉到的部分,
**调用方无法区分"数据全 vs 截断"**。

24-cell 矩阵这次没出现截断(`pagination_complete=True` 全 24/24),但 wrapper 本身没有
完整性标记 — 一旦服务端抖动,调用方会**默默**接受残缺数据。

#### 问题 C:`tbl_tick` PK 用 wrapper 自产 seqId,重抓时混合新旧

`seqId` 是 wrapper 从 0 起累加的(代码 `_enrich_ticks:546`)。这意味着:

- 第一次抓:seqId = 0..N-1,对应服务端数据 1..N
- 服务端增加了一笔成交(数据 1..N+1)
- 第二次抓:wrapper 重新从 0 累加,seqId 0 对应的还是数据 1,但 seqId N 现在对应数据 N+1
- **旧 seqId=N 的数据库记录(原数据 N)被 `INSERT OR IGNORE` 跳过,新数据 N+1 写入 seqId=N**
- → **DB 永远指向旧数据**(因为 seqId 0..N-1 都没变,只是 N 之后错位)

更进一步:服务端某笔成交消失了(比如撤单),wrapper 抓到 N-1 条,seqId 0..N-2 全对,
**最后一条新成交写不进 PK 范围** → 整张表少了末尾一条且没人察觉。

### 1.3 已有 GPT 评审回执中的关键判断(2026-09-18)

- "保留现有列表接口兼容调用方,新增 `get_history_ticks_with_meta()`" ✅ 已完成
- "原样保留 `buyorsell=5/8`、零量记录和重复记录,不擅自映射或删除" ✅ 已遵守
- "页失败或触顶时禁止落库和标记完成" ⏳ 待本方案落地
- "重抓使用新版本数据库或按"股票日"原子替换;现有 `force + INSERT OR IGNORE` 会混合新旧 seqId" ⏳ 本方案核心
- "先做多股票、多日期、六服务器、多时点矩阵验收,再确定服务器策略" ✅ 24-cell 已完成

## 2. 决策记录

### 决策 1:新建 `tbl_tick_v2`,保留旧表只读

- **方案 C-a(已批准)**
- 旧 `tbl_tick` 改为 `tbl_tick_legacy`,仅供历史数据查询,**不再写入**
- 新 `tbl_tick_v2` 用新 PK,新逻辑写入
- 旧 → 新迁移脚本单独排期,不在本方案范围内

### 决策 2:新 PK = `(ts_code, trade_date, time, seqId_in_minute)`

- **方案 PK-1(已批准)**
- `seqId_in_minute`:同一分钟内单股的 wrapper 自增序号(0..K-1,K = 该分钟内成交笔数)
- 含义从 v1 的"全局当日序号"改成"当日单股单分钟序号"
- 物理保证:**重抓同 `(ts_code, trade_date, time, seqId_in_minute)` 一定对应**同一**业务成交**
  (TDX `time` 字段精度只到分钟,服务端不可能在同一分钟内重排)
- `INSERT OR REPLACE` 现在是安全的:同 hash 表示同一笔成交,直接覆盖

### 决策 3:落库 gate = `meta.pagination_complete == True`

- 已实现:`fetch_history_ticks_with_meta()` 返回 `TicksFetchMeta`
- 新增 helper:`is_safe_to_persist(meta) -> bool`
- **任何** `pagination_complete=False` 的 fetch 结果,**禁止**写 `tbl_tick_v2`
- 调用方必须显式调用 gate,失败时上抛 `IncompleteDataError`

### 决策 4:不做的事情(明确划线)

- ❌ 不修改 `tdx_client.py:148-164` 的 IP 选择 `random.choice` 行为
  (GPT 建议属于"服务器可靠性"范畴,不影响"数据正确性")
- ❌ 不映射/删除 `buyorsell ∈ {5,8}` 的记录
- ❌ 不映射/删除 `vol=0` 的集合竞价记录
- ❌ 不映射/删除任何"看起来像噪声"的条目

## 3. 新 PK 设计细节

### 3.1 `tbl_tick_v2` schema

```sql
CREATE TABLE tbl_tick_v2 (
    ts_code TEXT NOT NULL,        -- '000001.SZ'
    trade_date TEXT NOT NULL,     -- '2026-08-27'
    time TEXT NOT NULL,           -- '09:31' (HH:MM,精度只到分钟)
    seqId_in_minute INTEGER NOT NULL,  -- 0..K-1,同分钟内单股自增
    datetime TEXT NOT NULL,       -- '2026-08-27 09:31:00' (由 time 推回,确定性)
    price REAL NOT NULL,
    vol INTEGER NOT NULL,
    buyorsell INTEGER,            -- 服务端原始值,0/1/2/5/8 都允许
    fetch_seq INTEGER NOT NULL,   -- 重抓时递增,审计用(详见 3.3)
    fetched_at TEXT NOT NULL,     -- ISO 写入时间
    fetched_host TEXT NOT NULL,   -- '180.153.18.170'
    fetch_complete INTEGER NOT NULL,  -- 1 = pagination_complete,0 = 截断
    PRIMARY KEY (ts_code, trade_date, time, seqId_in_minute)
);
CREATE INDEX idx_tick_v2_ts_date ON tbl_tick_v2(ts_code, trade_date);
```

### 3.2 `seqId_in_minute` 计算规则

```python
from collections import defaultdict

def compute_seq_in_minute(sorted_ticks: list[dict]) -> None:
    """原地修改 ticks,给每条加 seqId_in_minute 字段
    输入要求:按 time 字段升序(时间正序)
    同 ts_code + trade_date 下,每进入一个 (time) 分钟,seqId_in_minute 重置为 0
    """
    counters: dict[str, int] = defaultdict(int)  # key = ts_code + '|' + trade_date + '|' + time
    for r in sorted_ticks:
        ts_code = r["ts_code"]
        trade_date = r["trade_date"]
        time = r["time"]
        key = f"{ts_code}|{trade_date}|{time}"
        r["seqId_in_minute"] = counters[key]
        counters[key] += 1
```

**幂等性**:同一组输入,无论跑多少次,产出 `seqId_in_minute` 完全一致。

### 3.3 `fetch_seq` 的语义

- `fetch_seq` = 该 `(ts_code, trade_date)` 历史上第几次被 fetch 过
- 第一次成功 fetch:fetch_seq=1
- 第二次成功 fetch(覆盖):fetch_seq=2
- **从未成功 fetch**(paged 截断):不更新 fetch_seq
- `INSERT OR REPLACE` 时,新记录的 `fetch_seq` 覆盖旧的(说明是更新版本)

### 3.4 `fetch_complete` 的语义

- `1` = `pagination_complete=True`(数据完整)
- `0` = `pagination_complete=False`(截断,**这条记录本身就不能落库,所以 0 应该不存在**)
- 加这个字段是**冗余**的保险:即使未来 gate 漏了,DB 里也能用这个字段反查可疑行

### Step 2:`tdx_ticks_meta.py:fetch_history_ticks_with_meta` 改 enrichment

`_enrich_ticks` 之后,新增调用 `compute_seq_in_minute`,把每条 tick 的 `seqId` 改为 `seqId_in_minute`。

调用方若仍需要"当日全局序号",可以在自己的 layer 加一次累加。

## 5. 兼容性影响

### 5.1 调用方需要知道的事

- `seqId` 字段**含义改变**(全局 → 分钟内),且改名 `seqId_in_minute`
- 旧代码若按"当日全局序号"用 seqId 排序,会得到**乱序**(因为同一分钟内多个 seqId)
- **正确**排序:用 `time` 字段(字符串 `"HH:MM"` 字典序即时间序)

### 5.2 不影响

- `ts_code / trade_date / datetime / time / price / vol / buyorsell` 字段含义不变
- 旧 `tbl_tick_legacy` 表保留只读,所有历史查询继续可用

## 7. 风险与回滚

### 7.1 风险

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| 旧调用方依赖 `seqId` 全局语义 | 中 | 数据按时间排序错乱 | docs 显著标注字段变更;grep 全项目 `\.seqId\b` |
| 新 PK 唯一性假设被破坏 | 低 | `INSERT OR REPLACE` 误覆盖 | TDX 服务端 time 字段精度只到分钟,服务端不可能在同一分钟内重排;理论保证 |
| 落库 gate 漏调 | 低 | 残缺数据写入 DB | `fetch_complete=0` 字段作为冗余保险,可通过 SQL 反查 |
| 迁移脚本与新写入并发 | 低 | 双写竞态 | 本次不迁移,旧表只读,无并发 |

### 7.2 回滚步骤

如果新 PK 在生产出问题:

1. 停用 `tbl_tick_v2` 写入(只需 `data_gen` 改回)
2. 重命名:`ALTER TABLE tbl_tick_v2 RENAME TO tbl_tick_v2_disabled`
3. `ALTER TABLE tbl_tick_legacy RENAME TO tbl_tick`(恢复旧 PK)
4. 全过程不丢数据,只是新写入停了
